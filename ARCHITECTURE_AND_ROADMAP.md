# AeroTwin architecture and roadmap

## Current implementation

`pnpm edge` launches **three processes**: a Vite dashboard, a ground Express process on `API_PORT` (default 3001), and an onboard simulator process. The onboard process does not import or train the Random Forest and does not open SQLite. Every 150 ms it samples the simulated engine, passes values through the CAN-FD encoder/decoder, computes the physics baseline and residuals, evaluates instantaneous fault candidates, and obtains a simulated ECU status. It POSTs a reduced JSON payload (decoded signals, residuals, instantaneous candidates, ECU/CAN counters; **no raw frames**) to `/internal/telemetry`. The ground process verifies the signed envelope, applies per-source temporal fault rules and the RF model, combines physics/RF scores, generates advisories, stores SQLite records, and serves reports and the dashboard API. A stale or missing onboard stream produces HTTP 503 on `/api/telemetry?edgeMode=true`; the Edge mode SSE stops sending until fresh data arrives. The regular non-edge simulator, endurance runs, and scripted scenarios remain in the ground process for comparison and existing tests; they are **not** split-mode acquisitions. Edge mode uses onboard default controls and cannot currently apply dashboard control sliders or run an endurance stream; its toggle is a viewing selector, not an onboard command channel.

Production build: `pnpm build` emits `dist/index.js` (ground) and `dist/onboard.js` (onboard). Run `pnpm start` and `pnpm start:onboard` as separate services with the same `AEROTWIN_LINK_KEY`, and serve the dashboard from ground. Persist `AEROTWIN_DB_PATH` on a private volume; SQLite is local to the ground process. The `pnpm edge` launcher creates an ephemeral link key when none is supplied **for local development only**. It also runs Vite, so it is not a production supervisor. Both services require persistent Node processes and a durable ground-side volume; the split runtime is not directly deployable as a stateless/serverless function.

## Trust boundaries and configuration

- Set independent high-entropy secrets `AEROTWIN_LINK_KEY` (32+ characters, identical on both services), `AEROTWIN_OPERATOR_TOKEN`, `AEROTWIN_MAINTENANCE_TOKEN`, and `AEROTWIN_SESSION_KEY` (each 32+ characters; distinct role tokens). Provision as process secrets, never commit them. Production ground refuses to start without both role tokens and a session key; onboard refuses to start without a link key. Development without role tokens intentionally permits unauthenticated API access to retain the original test/demo workflow and logs a warning; **do not expose that mode to a network**. For production, set `NODE_ENV=production` for ground, restrict inbound `/internal/telemetry` with a firewall/reverse proxy as well, and terminate HTTPS at a trusted proxy. The onboard sender refuses non-loopback HTTP URLs (`AEROTWIN_GROUND_URL` defaults to `http://127.0.0.1:3001`).
- The HMAC-SHA256 covers the **exact serialized envelope bytes** `{source,sequence,sentAt,payload}`. Ground checks the signature in constant time before parsing, rejects timestamps outside a 30-second window, checks basic payload shape and advances a monotonic per-source sequence in SQLite. Duplicate/out-of-order packets remain rejected across ground restarts; an onboard restart gets a fresh source UUID. Key rotation requires updating both processes together. Link payloads are authenticated but **not encrypted by HMAC**; use loopback/Unix networking or HTTPS for remote links. There is no mutual TLS, hardware identity attestation, offline queue, reliable delivery, CAN-bus authentication, or cryptographic proof that simulated measurements represent a physical engine. A stolen link key allows forged telemetry. Signed telemetry can still be delayed/lost; ground marks it stale after five seconds. The 30-second validity window depends on synchronized clocks.
- API `/api/*` (except `/api/health` and `/api/auth/*`) accepts Bearer tokens or an eight-hour HttpOnly, SameSite=Strict session cookie exchanged at `/api/auth/session`. `/api/auth/status` reports whether sign-in is required. Operator can read and run/decide missions and scenarios; maintenance can read and POST fault records. Other writes are rejected by role. Cookies use Secure in production; cross-origin cookie writes are denied, but TLS, network exposure controls, token rotation, brute-force throttling, granular per-user audit logs, and a dedicated identity provider are **not** supplied. Tokens represent shared roles, not individuals. The existing dashboard workspace selector is a display preference, **not** a role grant; server-side checks determine actual permissions. Health is public and exposes no database path. `/api/auth/logout` clears the session cookie. Do not send tokens in URLs or store them in browser storage.
- The browser uses a cookie after sign-in because native EventSource cannot send Authorization headers. For API automation use `Authorization: Bearer <token>`. Access to local SQLite and logs must be controlled at the OS/deployment layer; neither is encrypted by AeroTwin.

## ECU / CAN adapter boundary

`server/ecu-interface.ts` exports `CanAdapter.readCycle(controls, tSeconds)` and `EcuAdapter.step(controls, tSeconds)`, plus `createSimulatedCanAdapter(engine)` and `createEcuInterface()`. `server/onboard-pipeline.ts` accepts replacement adapters and still runs `decodeFrames` integrity checks. A SocketCAN/python-can bridge should collect **one complete cycle** of five 29-bit CAN-FD frames, preserve identifier/DLC/data bytes, supply them via `readCycle`, map actual OEM command/heartbeat/fault-word messages in an `EcuAdapter`, and specify scheduling, dropped-frame handling, and bus error recovery. Do **not** connect the demo ECU command logic to a flight controller; the message IDs and signal scaling below are simulated and require OEM DBC verification and safety certification for hardware. This synchronous adapter interface is for a local queued bridge; production asynchronous bus I/O would need bounded buffering and deadline handling. CRC/counters validate demo frame integrity, not source authenticity.

### DBC-style simulated signal map

All IDs are extended 29-bit, J1939-style priority 6, proprietary PGNs 0xFF50–0xFF54, source address 0xE5. All signals are little-endian/Intel, unsigned 16-bit unless noted. Start bits count from bit 0 at byte 0. Engineering value = raw / `scale` + `offset`. Byte 0 low nibble is the rolling alive counter (0–15); high nibble unused. Last byte is CRC-8 SAE-J1850 over the four little-endian ID bytes followed by all data bytes except the CRC. Unused bytes are 0xFF. Frame DLCs below are **byte lengths**, not DLC nibble codes.

| ID / frame | Length | Signals: start bit / raw type / scale / offset / engineering unit |
| --- | ---: | --- |
| `0x18FF50E5` EEC_SPEED_LOAD | 12 | rpm 8/u16/4/0/rpm; map 24/u16/1000/0/bar; fuelFlow 40/u16/100/0/L/h; injectionTiming 56/i16/100/0/deg; altitude 72/u16/2/-1000/ft |
| `0x18FF51E5` CYL_TEMPS | 20 | cht1..cht4 at 8,24,40,56; egt1..egt4 at 72,88,104,120; each u16/10/-40/deg C |
| `0x18FF52E5` LUBRICATION | 8 | oilPressure 8/u16/100/0/psi; oilTemp 24/u16/10/-40/deg C |
| `0x18FF53E5` VIBRATION | 12 | vibration 8, vibOrderHalf 24, vibOrder1 40, vibOrder2 56; each u16/100/0/mm/s |
| `0x18FF54E5` ELECTRICAL | 8 | batteryVoltage 8/u16/100/0/V; alternatorHealth 24/u8/1/0/percent |

Source of truth for actual frame encoding and integrity checks: `server/can-fd.ts` (`FRAME_SPECS`). This document is a human-readable integration map, not a downloadable OEM DBC file.

## Roadmap / limitations

1. Connect and validate a hardware adapter against an OEM DBC, authenticated command path, recorded bus traces, sensor failure injection and independent safety interlocks. No real hardware is connected today.
2. Add bounded link buffering/backpressure, signed control-plane commands, key rotation, service identity/mTLS and operational metrics/alerts before remote deployment.
3. Replace shared role tokens with individually attributable accounts, audit trails, per-mission authorization, rate limits and security testing before operational use.
4. Evaluate model calibration on independently collected flight data; the current RF is trained on simulator/dataset inputs and its health/RUL outputs are research demonstrations, **not airworthiness decisions**. Federated averaging is not implemented; it remains an optional future demo, not a deployed learning path.
